# [DX] Add offline provider-schema validation to tests

## What this card solves

Export tests today check that the YAML parses and round-trips. The review showed that isn't proof: a GitLab stage named `stages` round-trips perfectly while replacing the stages list with a job (AR-15). The product doc sets the closure gate for export findings as **offline provider-schema validation plus real builds**, since agents can't dispatch hosted pipelines.

This card adds the validation harness TASK-024 selected, as a test helper that every export card (026 to 028) uses: `expectValidGithubWorkflow(yaml)` and `expectValidGitlabCi(yaml)`. It adds no product behavior.

## Test criteria

Backend (Jest), a new `ci-export/provider-schema.spec.ts`. Use the AC IDs from TASK-024.

```ts
describe('T-CIEXPORT-### — provider schema harness', () => {
  it('accepts every current golden GitHub Actions export')
  it('accepts every current golden GitLab CI export')
  it('rejects a GitLab document whose `stages` is a mapping')
    // Assert: expectValidGitlabCi('stages: {a: 1}') throws with a schema path in the message
  it('rejects a GitHub workflow with `on.push.branches` as a string')
  it('runs with network disabled')
    // Assert: schemas load from a vendored file path, no fetch/http call
})
```

## Implementation plan

- Dependency: the tool(s) TASK-024 named. This is a **new dev dependency**, so ask the owner with the name and version before installing (Layer 1 guardrail, `GUIDELINES.md` § Dependencies). If a JSON schema is vendored instead, store it under `backend/test-support/schemas/` with its source URL and retrieval date in a header comment.
- New helper `backend/src/modules/ci-export/provider-schema.ts` (or under `test-support`, if that is where TASK-024 places it), exporting the two assertion functions.
- Wire the helper into the existing export suites (`ci-export/export.spec.ts`, `workspace-bundle/workspace-bundle.spec.ts`). Assert on current output first: failures found at this point are Phase 4 bugs, so record them in the handoff and don't fix them here.
- Validation: `pnpm --dir backend test`, then `pnpm check`.
- Size: ~60 production lines (helper); vendored schemas are data, not counted.
- Out of scope: fixing exporter output (TASK-026 to 028).

## Attention points

- The CI workflow runs Node 20 with no special tooling. A Go binary like actionlint needs an install step in `ci.yml`, which is a **protected file**. Prefer a pure-Node option, or ask the owner before touching CI.
- A vendored schema drifts from the provider over time. Record the version and date so the drift is visible.
- ❌ Don't call hosted linters (the GitLab CI Lint API). Repo content must not leave the machine (Layer 1).
