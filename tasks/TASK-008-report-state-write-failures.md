# [FIX] Report state write failures instead of acknowledging (AR-07)

## What this card solves

When the store can't write (a read-only disk, a file where the data directory should be, disk full, no permission), it swallows the error, returns a saved record anyway, and the API answers 200. The frontend then shows "Saved" for data that never reached disk. Review probe R18 shows it: after an acknowledged save, a new store can't restore anything.

Persistence may stay non-fatal (editing must keep working), but it must stop claiming durability. `StateStore.write` reports failure, and `PUT`/`DELETE /api/state/pipeline` return a retryable failure envelope instead of a success body. The frontend half (showing that state) is TASK-010.

## Implementation plan

- `backend/src/modules/state-store/store.ts:126-137` `write()`: stop swallowing errors. Throw a `StatePersistenceError` declared in a new `state-store/errors.ts` (`GUIDELINES.md` § Error handling). Keep the tmp+rename atomicity.
- `savePipeline` (`:58-68`) and `deletePipeline` (`:70-76`): update the in-memory map only after a successful write, so memory and disk stay the same.
- `appendRun` (`:89-94`): run history is a convenience (`editor-api/run-registry.ts:142-156` already catches). Keep it non-fatal, but log it.
- `backend/src/modules/editor-api/state.controller.ts:53-66,71-76`: catch `StatePersistenceError` and map it through `httpError()` to the code TASK-006 adds to the closed `ErrorCode` union in `editor-api/http-errors.ts`.
