# [FIX] Make the visibility marker symlink-safe (AR-01)

## What this card solves

Before any stage runs, the executor proves that Docker can see the temporary workspace copy. It does this by writing a marker file into the copy and reading it back from a throwaway container. The marker always has the same name (`.pipe-editor-visibility-probe`), and the copy keeps symlinks as symlinks. A project that ships a symlink with that name therefore makes the backend overwrite whatever the link points to, including a file outside the copy, **before** anything runs. The overwrite happens even if the probe then fails.

The fix creates the marker so that it can't follow a link: an unpredictable name, exclusive creation that refuses existing entries, and a check that what was opened is a regular file. Cleanup removes only the file this operation created. The rejected alternative was to delete any existing entry with the marker name first. That still races, and it destroys a user's file.

For the user, scanning and running an untrusted repository can no longer modify files outside the copy through this path.

## Attention points

- `O_NOFOLLOW` exists on Linux and macOS, but the check must not rely only on it. Also verify with `fstat` that a regular file was opened.
- The probe container mounts the copy read-only (`:104-105`). Keep that. The new marker name must not collide with project files; with a UUID suffix, a collision needs a deliberate guess.
- ❌ Don't `unlink` whatever sits at the marker path before creating it. That is the same class of bug (it destroys user data).
- Backward compatibility: stages never see the marker, because it is removed before stages run. Nothing else depends on the name.

## Observability

- No other instrumentation: the probe outcome is already surfaced through `WorkspaceNotVisibleError`.
