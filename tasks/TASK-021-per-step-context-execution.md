# [FIX] Keep per-step env and directory in execution (AR-12)

## What this card solves

An imported stage can have steps with different env maps and working directories. That's common in GitHub Actions, where each step sets its own `env:` and `working-directory:`. The executor merges every step's env into one container env and uses only the first step's directory. Step one with `MODE=one` in `one/` and step two with `MODE=two` in `two/` both run with `MODE=two` in `/workspace/one` (review probe R06).

The product doc decided that per-step context is kept everywhere (EXEC-FR-008 superseded by TASK-014). The stage keeps one container. The generated script switches directory and env per step inside that container: each step runs in a subshell with its own `cd` and exported variables, under `set -e`. The rejected alternative was one container per step. It changes the workspace-sharing and timing semantics users rely on, and costs a container start per step.

## Implementation plan

- `backend/src/modules/executor/execute.ts`:
  - `:215-218`: stop merging `step.env` into the container env. The container env becomes `BASE_ENV` (+ `COREPACK_HOME`) only.
  - `:240-243`: build the script per step. For each step, emit a subshell that changes to the step's quoted directory, loads that step's env through the transport TASK-014 specifies, and runs the step. Join the subshells with newlines under `set -e`.
  - Quote with a shell-quote helper, and never interpolate raw IR strings into the shell (`GUIDELINES.md` § Security). Reuse the existing `shellQuote` (used in `workspace-bundle/generate.ts:288`) by moving it to a shared place rather than copying it.
  - `:302-307` `resolveWorkingDir`: the container `WORKDIR` stays `/workspace`, and per-step directories are applied in the script.
- `stage-started` events (`:251-257`) carry `shellCommand`. The UI shows it, so keep it readable.
- Validation: `pnpm --dir backend test -- executor`, then `pnpm check`.
- Size: ~100 production lines.
- Out of scope: exporters (TASK-022) and Dockerfile (TASK-023).

## Attention points

- A subshell per step means `cd` and variables don't leak between steps. That matches GitHub's per-step semantics. Document it in the spec amendment, not only in code.
- Inlining `export K=v` would put env **values** into `shellCommand`, which is emitted in `stage-started` events and shown in RunPanel, so secrets could be displayed. Follow the transport TASK-014 specifies instead, for example per-step env files written into the temp copy and sourced inside the step's subshell. The displayed command shows env **keys** only.
